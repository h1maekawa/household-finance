## 0. 結論サマリ

**要件書で「追加すべき」とされた6テーブルのうち、実際に新規なのは `wish_items` 1つだけです。**
残り5つは既に存在するテーブルと同じものを別名で作ろうとしています。このまま実装すると
データモデルが二重化し、「①データの正確性を最優先」という実装ポリシー自体を壊します。

| 要件書の提案 | 実際の状況 | 判断 |
|---|---|---|
| `fixed_expenses` | **`scheduled_payments` が完全に同じ**。要件書§固定費管理の11項目は migration 020 で全て実装済み | ❌ 作らない |
| `goals` | `life_goals`（019）が同一概念 | ❌ 作らない |
| `missions` | `life_goals` + `debts` でほぼ表現できる | ⚠️ §3で検討 |
| `ai_context` | `ai_user_memory`（019）が同一概念 | ❌ 作らない |
| `ai_recommendations` | `ai_insights`（019）が同一概念 | ❌ 作らない |
| `wish_items` | **存在しない** | ✅ 新規作成 |

同様に「ダッシュボード改善: 毎月予算カードをトップへ追加」も**既に実装済み**です
（`components/BudgetCard.tsx` + `lib/services/budget-engine.ts` の `computeBudget`）。
追加ではなく、後述§2の**計算モデルの修正**が必要な状態です。

**本当に新規で価値があるのは3つ**: ① Wish List ② 購入シミュレーション ③ AI優先順位。
この3つに集中し、他は既存の延長で実装するのが最短です。

## 1. 【DB設計】重複の解消

### 1.1 `fixed_expenses` は作らない — MUST

要件書§固定費管理の管理項目と、`scheduled_payments` の現状を突き合わせると**完全一致**します。

| 要件項目 | 既存カラム |
|---|---|
| 名称 / カテゴリ / 金額 / 支払日 | `name` / `category` / `amount` / `due_day` |
| 支払方法 | `payment_method`（020） |
| 引落口座 | `debit_account_id` → `accounts`（018） |
| 繰り返し | `recurrence`（020） |
| 開始日 / 終了日 | `start_date` / `end_date`（020） |
| 有効フラグ / メモ | `is_active` / `memo` |

加えて `business_day_rule`（営業日補正）・`currency`/`foreign_amount`（ジブラルタ105USD）・
`credit_card_id`（楽天モバイルのカード払い）まで実装済みで、要件書の登録予定7件は
**そのまま登録できます**。新テーブルを作ると、キャッシュフロー予測・コーチ・予算エンジンが
参照している既存の経路（`lib/services/fixed-costs.ts`）から切り離されます。

### 1.2 `wish_items`（唯一の新規）— MUST

```sql
create table if not exists wish_items (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  title text not null,
  amount integer,                       -- 整数円。未確定は null
  priority integer not null default 3,  -- 1〜5（★の数）
  reason text,                          -- 「必要な理由」
  desired_by date,                      -- 希望購入時期
  kind text not null default 'purchase'
    check (kind in ('purchase', 'experience')),   -- §1.4 参照。投資は含めない
  status text not null default 'wanted'
    check (status in ('wanted', 'planned', 'purchased', 'dropped')),
  purchased_at date,
  memo text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index if not exists wish_items_user_status_idx
  on wish_items (user_id, status, priority desc);
```

- `status` を持たせるのが要点。「買った/やめた」が残らないと**AIの学習材料が消えます**。
  将来の ROI 分析（要件書§今後追加予定）は購入後の満足度フィードバックが前提です。
- 価格推移（楽天/Amazon/Yahoo最安値）は `wish_price_history` を別テーブルで後付けできる形にし、
  今は作らない。外部スクレイピングは規約・保守コストが高く、V3.1のスコープに合いません。

### 1.3 `missions` は作らず `life_goals` を拡張 — SHOULD

要件書のミッション例を分解すると:

| ミッション例 | 既存での表現 |
|---|---|
| 親へ50万円返済 | `debts`（direction='borrowed', counterparty='親'）※既に設計済み |
| 生活防衛資金100万円 | `life_goals`(kind='savings', target_amount=1000000) |
| 年間100万円投資 | `life_goals`(kind='savings') + `investment_transactions` の実績 |
| AIアプリ開発資金 / 引越し資金 | `life_goals`(kind='custom') |

新テーブルではなく **`life_goals.kind` に `'debt_repayment'` を追加し、`debts` への参照を1本持たせる**
のが最小の変更です。

```sql
alter table life_goals
  add column if not exists debt_id uuid references debts(id) on delete set null;
```

これで要件書§ミッション管理の表示例（残高50万 / 進捗20% / 今月返済4万 / 完済2027年7月）は、
既存の `computeGoalProgress`（`lib/services/goal-progress.ts`、達成月の線形予測を実装済み）が
そのまま出せます。**「ミッション」は新機能ではなく `life_goals` のUI上の呼び名**にすべきです。

### 1.4 Wish List に投資商品を混ぜない — MUST（重要）

要件書の Wish List 例に **「NVIDIA株 150,000円 ★★★★★」** が入っています。これは分離が必要です。

- 消費財（MacBook・Apple Watch）への「今月買えます」は、**残高と生活防衛資金の事実提示**です。
- 個別株への「今月買えます／来月推奨」は、**銘柄と時期を指定した投資助言**になります。
  これは金商法上のリスクがあり、`docs/v3-architecture-review.md` §9 でも
  「投資助言は一般情報であり保証しない」をシステムプロンプトに固定する方針が既に決まっています。

**推奨**: `wish_items.kind` に投資を含めない（上のDDLは `purchase`/`experience` のみ）。
投資予定額は既存の `budgets.investment_target` で扱い、Wish List とは別導線にする。
AIは「投資に回せる余力は月3万円です」（事実）までを言い、
「NVIDIAを今月買うべき」（助言）は言わない、という線引きを設計に埋め込んでください。

## 2. 【要件の不整合】毎月予算カードの計算モデル

要件書のダッシュボード例をそのまま実装すると**変動費が二重に引かれます**。

```
給与              251,225
固定費             87,328   ← 引く
変動費             32,500   ← 引く（①）
自由に使えるお金   131,397   = 251,225 - 87,328 - 32,500
今月使用済み       48,320   ← さらに引く（②）
今月残り           83,077   = 131,397 - 48,320
```

①の「変動費32,500」が**予定**で、②の「使用済み48,320」が**実績**なら、同じ変動費を2回
差し引いています。実際、要件書§変動費管理の内訳合計は **31,500円**（18,300+7,200+3,500+2,500）で、
カードの32,500円とも一致していません。

**既存 `computeBudget` の式が正しい**ので、そちらに寄せるべきです（`types/budget.ts` の `BudgetSummary`）:

```
変動費の枠 = 収入 − 固定費 − 投資目標 − 貯蓄目標 − 予備費
残り       = 変動費の枠 − 変動費の実績
```

つまりカードに出すべきは「変動費（予定）」ではなく **「投資・貯蓄・予備費」** です。
`BudgetCard.tsx` は既にこの5行を表示しています。要件書の意図（給与→固定費→変動費→自由）に
近づけたいなら、**ラベルの変更**で足りて、計算式を変える必要はありません。

### もう1つの二重計上リスク

固定費分析の合計に **楽天モバイル 3,890円** が含まれています。これはカード払いなので、
カード請求見込みにも同額が乗ると二重計上になります。`lib/services/fixed-costs.ts` の
`resolveMonthlyDebits` は既にこの付け替えを実装済みなので、**固定費分析の集計も必ず
この関数を通してください**。UIやAPIで独自に `SUM(amount)` すると壊れます。

## 3. 【AI設計】購入判断をどう決定的に作るか

`docs/v2-ai-coach-spec.md` の原則「**決定的エンジン + LLMナレーション**」をここでも守ります。
購入可否の判断は計算であり、LLMにさせてはいけません。

### 3.1 純関数として作る — MUST

`lib/services/purchase-simulator.ts`（新規）

```ts
export type PurchaseVerdict = {
  affordable: boolean
  balanceAfter: number            // 購入後の口座残高
  emergencyFundMonths: number     // 生活防衛資金（何ヶ月分）
  investableAfter: number         // 購入後に投資へ回せる額
  upcomingDebitsCovered: boolean  // 直近の引き落としを賄えるか
  reasons: string[]               // 判定根拠（決定的な文字列）
}

export function simulatePurchase(
  item: WishItem,
  ctx: { accounts, budget, upcomingDebits, monthlyFixedCost, goals },
): PurchaseVerdict
```

要件書§購入シミュレーションの表示（残高230,000 / 防衛資金2.5ヶ月 / 投資可能30,000 / 評価）は
**全てこの純関数の出力**で、LLMは不要です。既存の資産が揃っているので実装は薄く済みます:

- 口座残高 → `listAccountsWithBalances`（`lib/repositories/accounts.ts`）
- 直近の引き落とし → `loadUpcomingDebits`（`lib/services/budget-loader.ts`、営業日補正・カード付替済み）
- 自由予算 → `computeBudget`
- 目標進捗 → `computeGoalProgress`

**生活防衛資金の定義を先に決めてください**（未決事項）。
「総現金 ÷ 月間固定費」か「÷（固定費+変動費平均）」かで月数が倍近く変わります。
推奨は後者（生活費ベース）。要件書の例（残高230,000で2.5ヶ月）は月92,000円想定＝固定費のみに近く、
実態より楽観的に出ます。

### 3.2 AI優先順位は「スコア関数」であってLLMではない — MUST

要件書§AI優先順位（①親への返済 ②生活防衛資金 ③投資 ④MacBook ⑤Apple Watch）は、
毎月変わる順位です。LLMに並べさせると**同じ入力で毎回順序が変わり**、信頼を失います。

`lib/services/priority-engine.ts`（新規・純関数）で、
`life_goals.priority` / `target_date` の近さ / `debts` の期限 / `wish_items.priority` /
`desired_by` を決定的にスコア化して並べ、LLMは**並んだ結果を日本語にするだけ**にします。

将来の ROI分析（人生への影響・使用頻度・生産性・緊急度）も、**ユーザーが入力した点数**を
重み付き合計するだけにしてください。LLMに点数を発明させると根拠のない数字が出ます。

### 3.3 常駐AI「Piro AI」— 既存方針のとおり

`docs/v3-architecture-review.md` §6.5 の構成（`lib/ai/` に provider / context / tools / prompts）が
そのまま使えます。v3.1で追加すべきツールは3つだけ:

- `get_wish_list()` — Wish List と優先順位
- `simulate_purchase(itemId)` — §3.1 の純関数を呼ぶだけ
- `get_missions()` — `life_goals` + `debts` の進捗

`ai_conversations` / `ai_messages` は未作成なので、ここは新規テーブルが必要です（§5.4に設計済み）。

## 4. 【パフォーマンス】

`wish_items` / `life_goals` は数十件規模なので、ここがボトルネックになることはありません。
**実際の懸念は変わらず `/api/cashflow`** です（`docs/v3-architecture-review.md` §10）。

新たに増えた負荷が1つあります: `lib/services/fixed-costs.ts` の `toDebitSources` は
前月・当月・翌月の3ヶ月ぶんを毎回解決します。固定費が数百件なら数百×3の純粋計算で問題ありませんが、
**購入シミュレーションを「入力するたび」に走らせるとAPIを何度も叩くことになります**。
シミュレーションはクライアント側でデバウンスするか、コンテキスト（残高・予算・引落）を
1回取得して**クライアントで純関数を再実行**する形にしてください
（純関数なのでサーバー/クライアント両方で同じ結果が出ます — これが純関数設計の利点）。

## 5. 【UX】毎日開きたくなるか

Wish List は**この目的に対して最も効きます**。家計簿は「我慢の記録」になりがちですが、
Wish List があると「あと2ヶ月でMacBookが買える」という**前進の記録**に変わります。

- **MUST**: ホームに「次に手が届くもの」を1つだけ出す。5件並べると選択疲れになります。
- **SHOULD**: 節約が Wish List の達成日を早める形で見せる（「今月の外食を1回減らすと3日早まる」）。
  これは `simulatePurchase` の入力を変えて再計算するだけで出せます。
- **SHOULD**: 購入後に `status='purchased'` を記録し、「買ってよかったか」を1タップで残す。
  将来のROI分析の唯一の学習データになります。
- **COULD**: ミッション（親への返済）の進捗バー。要件書の完済予定2027年7月は
  `computeGoalProgress` が既に出せます。

**注意**: 要件書§AIコメントの「固定費率35% 非常に健全です」のような**断定は避けてください**。
固定費率の健全性は世帯構成・地域で大きく変わり、根拠のない太鼓判は信頼を損ないます。
「固定費率35%（先月比 -2pt）」のような**事実の提示**に留めるのが安全です。

## 7. 推奨する実装順序

```
Step 1  wish_items テーブル + CRUD API + Wish List画面
        （唯一の新規テーブル。単独で価値が出る）
   ↓
Step 2  lib/services/purchase-simulator.ts（純関数 + ユニットテスト）
        + 購入シミュレーションUI
        ※ 先に「生活防衛資金の定義」を決めること
   ↓
Step 3  lib/services/priority-engine.ts（純関数）
        life_goals に debt_id を追加し、ミッション表示を既存エンジンで出す
   ↓
Step 4  毎月予算カードのラベル修正（計算式は変えない）
   ↓
Step 5  lib/ai/ 基盤 + 常駐 Piro AI（v3.0レビュー §6.5 のとおり）
```

Step 1〜4 は**LLM不要**で、全て純関数とCRUDです。要件書の目玉である
「AIが購入タイミングを提案」は、実質 Step 2 の純関数で完成し、
Step 5 のLLMはその結果を喋らせるだけになります。これが最もコストが低く、精度が高い順序です。
