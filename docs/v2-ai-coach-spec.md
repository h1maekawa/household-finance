# Version 2.0 実装仕様 — AIライフプランナー・家計コーチ

Date: 2026-07-24
立場: プロダクトアーキテクト（ビジョン → 実装可能な設計への落とし込み）
関連: `docs/v3-architecture-review.md`（基盤設計）, `docs/budget-design.md`（予算設計）

> コンセプト: 家計を記録するアプリではなく、**人生の目標を実現するためにAIが家計を設計・伴走するアプリ**。

---

## 0. 最初に押さえる2つのこと（ここを外すと破綻する）

### 核心原則: 「決定的エンジン + LLMナレーション」
このコーチ機能の**9割は計算（決定的ロジック）、1割がLLM**です。逆にしてはいけません。

- 予算・進捗率・達成予測日・「三井住友に25万円残す」——**お金に関わる数字は全て純関数で計算**する。LLMには計算させない。
- LLMの仕事は2つだけ：(1) 計算結果を**自然な日本語に変換**、(2) 複数の洞察から**今日伝えるべき1つを選ぶ**。
- 理由: 精度（LLMは計算を間違える）・コスト（毎回の計算にLLMを使うと採算が合わない）・信頼（家計アプリで金額を間違えると即失う）。

この原則により、**Phase 3（コーチ）の大部分はLLMなしでも動く**。「食費が2,000円超過、外食を1回減らせば戻せる」はルールベースで出せる。LLMは文章を滑らかにするだけ。これがコスト設計と月額採算の鍵。

### 順序の罠: 花形AIは地味な土台の上にしか立たない
あなたのダッシュボード例の目玉コメント——
> 「来週は楽天カードの引き落としがあるため、三井住友銀行に25万円残しておくことをおすすめします」

これを出すには **口座別残高（`accounts`）+ カード引き落とし予測 + 予算** が全部必要です。今のアプリには口座別残高テーブルが無い（単一残高のみ）。**つまり一番"AIらしい"体験は、一番地味な口座データモデルの上にしか実装できない。**

だから体験としては「AIが主役」でも、**実装順序は 口座 → 予算 → 目標 → コーチ**。派手さに釣られて順序を逆にすると、コーチが薄っぺらい汎用コメントしか出せず差別化にならない。

|---|---|---|

## 2. データモデル（Phase別）

V3レビューで提案済みのテーブルを、このコーチ機能の観点で確定させる。DDLはスケッチ（本実装でRLS/grant/index付与）。

### 2.1 口座（V2.1・花形コメントの前提）— 既にV3レビュー §5.1 で提案
`accounts` / `account_balances`。`scheduled_payments.debit_account_id`・`credit_cards.debit_account_id` で「どの口座から引き落とすか」をFK化。
→ これで「◯日の引き落としまでに、その口座へいくら残すべきか」が計算できる。

### 2.2 予算（V2.1・Phase2の器）— 既に `budget-design.md` で設計済み
`budgets`（月次: 収入・固定費・投資・貯蓄・予備費・自由予算）。V2ではこれに**カテゴリ別サブ予算**を足す：
```sql
create table budget_categories (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  budget_id uuid not null references budgets(id) on delete cascade,
  category text not null,          -- '食費' '外食' ...
  amount integer not null,         -- 推奨予算（整数円）
  source text not null default 'ai', -- 'ai' | 'manual' | 'template'
  created_at timestamptz not null default now(),
  unique (budget_id, category)
);
```
→ Phase2のカテゴリ配分表（食費30,000円…）はこのテーブル。「AIが提案 → ユーザーが微調整」で `source` が ai→manual に変わる。

### 2.3 目標（V2.2・Phase1,2,5）— 既にV3レビュー §5.3 で提案
`life_goals`（kind, target_amount, target_date, monthly_contribution, assumptions jsonb）。
- Phase1の目標設定 → `life_goals` にinsert。
- Phase2の逆算（毎月いくら積む）→ `monthly_contribution` を計算して保存。
- Phase5の達成率・達成予測日 → `life_goals` + 実績から計算。

### 2.4 コーチの洞察（V2.3）— 既にV3レビュー §5.4 で提案
`ai_insights`（type, severity, title, body, payload jsonb, status, generated_for）。
- Phase3/4のコメント・提案はここに保存。日次バッチで生成、ユーザーは未読を消化。
- `payload` に構造化アクション（例: `{action:'keep_balance', account:'smbc', amount:250000, by:'2026-07-27'}`）を入れ、UIがバッジ・ボタン化できるようにする。

### 2.5 AIの記憶（V2.4）— 既にV3レビュー §5.4 で提案
`ai_user_memory`（profile jsonb: 価値観・重視点・リスク許容度）。オンボーディングの回答（Phase1①「何を重視するか」）をここに保存し、コーチの口調・優先度に反映。

### 2.6 目標達成のための貯蓄・投資の実績判定
目標進捗（Phase5）を出すには「目標に紐づく積立の実績」が要る。最小実装：
- 貯蓄目標 → `account_balances` の増加分、または特定口座残高で近似。
- 投資目標 → 既存 `investment_transactions` の買付合計。
- 精緻にやるなら将来 `goal_contributions`（目標への入金履歴）を足す（COULD）。

## 3. 各Phaseの実装仕様（計算 / API / AIの役割 を分離）

### Phase1 オンボーディング
- **UI**: 初回起動時のウィザード（ステップ: 重視点 → 目標 → 収入 → 固定費 → 変動費確認）。既存の `FlowSetupWizard.tsx` を土台にできる。
- **計算**: ⑤変動費の「平均52,000円」は**LLM不要**。過去N ヶ月の `transactions` をカテゴリ集計するだけ（既存 `/api/analysis/fixed-variable` の拡張）。
- **保存**: 回答 → `life_goals` / `budgets` / `users_profile` / `ai_user_memory`。
- **API**: `POST /api/onboarding`（一括保存）。
- **AIの役割**: なし（MVP）。将来、自由記述の目標をLLMで構造化（COULD）。

### Phase2 AI予算作成
- **計算（コア・決定的）**: `lib/services/budget-engine.ts`
  ```
  自由予算 = 収入 − 固定費 − 投資目標 − 貯蓄目標(=目標逆算額) − 予備費
  ```
  貯蓄目標額は `life_goals` から逆算：`(target_amount − 現在額) / 残り月数`。
- **カテゴリ配分**: MVPは**過去実績の比率 × 自由予算**で機械的に配分（LLM不要）。実績が無ければテンプレート比率。
- **API**: `GET /api/budget?month=…`（`budget-design.md` の設計）。`PUT /api/budget/categories` で微調整。
- **AIの役割（V2.4）**: 配分の説明・「外食を減らして娯楽に回す?」等の提案文。数値はエンジンが出す。

### Phase3 AIコーチ（日次）
- **計算（コア・ルールベース）**: `lib/services/coach-rules.ts`
  - 各カテゴリ: 予算・実績・進捗率・ペース（経過日数比）を算出。
  - ルール例（全てLLM不要）:
    - `progress_on_track`: ペース ≤ 1.0 → 「予算内に収まりそう」
    - `category_over`: 実績 > 予算 → 差額と「外食を1回減らせば戻せる」係数を計算
    - `upcoming_debit`: 引き落とし予定日−3日以内 → 「◯日に引き落とし、◯口座に◯円残す」
    - `transfer_suggestion`: 引き落とし口座の残高 < 引き落とし額 → 不足分の資金移動提案
  - 出力を `ai_insights` に保存。
- **実行**: **日次バッチ**（Vercel Cron / Supabase Edge Function）。全ユーザー分を夜間生成。ユーザーが開くたびにLLMを呼ばない（コスト）。
- **API**: `GET /api/coach/insights`（当日分の未読を返す）。
- **AIの役割（V2.4）**: ルールが選んだ洞察を自然文に。複数洞察から今日の1本を選ぶ優先度付け。

### Phase4 AI改善提案（週次）
- **計算**: 週次で支出パターンを集計（例: コンビニ利用18回23,000円 = `payment_method`/`memo` 集計）。「スーパー活用で約8,000円節約」の係数は**ルール/ヒューリスティック**で算出（過去のスーパー単価との差など）。
- **実行**: 週次バッチ → `ai_insights`（type=`weekly_suggestion`）。
- **AIの役割（V2.4）**: 提案文の生成と、押し付けがましくない口調の調整。

### Phase5 ゴール管理
- **計算（決定的）**: `lib/services/goal-progress.ts`
  - 達成率 = 現在額 / target_amount。
  - 達成予測日 = 現在額 + 月次積立ペース × 残り月 → target_amount に到達する月。
  - 「このままなら2030年11月に達成予定」は線形予測で出せる（LLM不要）。
- **API**: `GET /api/goals/progress`。
- **UI**: ダッシュボードの目標カード（進捗バー）。
- **AIの役割（V2.4）**: 予測のコメント化、遅れている時の建設的な提案。

### Phase6 ライフイベント（V3.x・今は設計だけ）
- `life_events`（V3レビュー §5.3）。キャッシュフロー（V3レビュー §8のイベント抽象）に入力として流し込む。
- 「引越し → 家賃増加 → 目標再計算」は、`life_events` が予算エンジン・目標逆算の入力になれば自動で効く。
- **今やること**: 実装ではなく、予算エンジンと目標逆算を「イベントを受け取れる純関数」として設計しておくこと（後付けで壊れない構造）。

## 4. AIコーチのアーキテクチャ（V2.4）

V3レビュー §6 の具体化。「何を計算し、何をLLMにやらせるか」の線引き。

```
[決定的エンジン（純関数・毎日バッチ）]
  budget-engine / coach-rules / goal-progress
        ↓ 構造化された洞察（ai_insights）
[LLMナレーション層（薄い・任意）]
  lib/ai/narrate.ts … 洞察 → 日本語 + 今日の1本を選定
        ↓
[常駐アシスタントUI（全画面右下）]
  app/layout.tsx に1つ設置。画面コンテキストを渡す。
```

- **コンテキスト**: LLMに全取引を渡さない。エンジンが出した「今日の洞察サマリ + ユーザー価値観（ai_user_memory）」だけ渡す（安価・高精度）。
- **ツール**: 常駐チャットで「今月の食費は?」等に答える時だけ集計ツールを呼ぶ（V3レビュー §6.2）。
- **安全**: 資金移動・取引・課金は**提案のみ、実行は人間**。`propose_transfer` は `ai_insights` に書くだけ。
- **プロバイダ抽象**: 用途別にモデル/APIキーを切替可能に（抽出=安いモデル、相談=賢いモデル）。「違うAPIキーで」の要望はここで自然に吸収。

## 5. MVP定義（最小で価値が出る習慣ループ）

**「目標を1つ設定 → 今月の予算が自動で出る → 毎日開くと進捗と一言コメント」** これだけで差別化は成立する。

MVPに**含む**:
- オンボーディング（目標1つ・収入・固定費・変動費確認）
- 予算エンジン（自由予算＋カテゴリ配分、決定的）
- ダッシュボードの目標カード＋カテゴリ進捗バー
- 日次コーチのルールベース・コメント（LLMなしでも可）
- 口座別残高（花形コメントの前提・最小1〜2口座）

MVPに**含まない**（後回し）:
- LLMナレーション（V2.4）— ルールの定型文で先に出す
- 週次改善提案（Phase4）
- ライフイベント（Phase6）
- 複数目標の同時最適化（まず1目標）

**判断基準**: 「毎日開きたくなるか」はコメントの賢さより**進捗が一目でわかること**で決まる。まず進捗の可視化を完璧にし、AIの言葉は後から乗せる。

## 6. ビルド順序（現実的な依存順）

V3レビューのPhase順と整合。上から順に。各段で単体で価値・検証可能。

1. **基盤是正（V3 Phase 0）**: RLS/service_role是正・整数円・インデックス。※保存バグ（migration 017未適用）もここで解消。
2. **口座モデル（V2.1）**: `accounts`/`account_balances`、`debit_account_id` FK化。
3. **予算エンジン（V2.1）**: `budgets`/`budget_categories` + 純関数エンジン + `/api/budget`。
4. **オンボーディング＆目標（V2.2）**: ウィザード + `life_goals` + 逆算計算。
5. **目標進捗（V2.2/Phase5）**: `goal-progress` + ダッシュボード目標カード。
6. **日次コーチ・ルール版（V2.3）**: `coach-rules` + `ai_insights` + 日次バッチ + `/api/coach/insights`。
7. **LLMナレーション＆常駐アシスタント（V2.4）**: `lib/ai/*` + layout常駐UI。
8. **週次提案・ライフイベント（V3.x）**: Phase4/6。

**横断**: 各エンジンは純関数＋ユニットテストで数値の正しさを担保（お金を扱うので必須）。

## 7. 決めるべき事項（先に決めると手戻りが減る）

1. **目標逆算の前提**: 投資評価額を目標額にカウントするか（値動きするので達成率が上下する）。利回り・インフレを見込むか、名目額の単純積立か。MVPは「単純積立・名目」を推奨。
2. **カテゴリ配分の初期値**: 過去実績比率 / テンプレート / AI提案 のどれを既定にするか。MVPは実績比率、履歴が薄い人はテンプレート。
3. **コーチの配信手段**: アプリ内バッジのみか、プッシュ通知（PWA/ネイティブ）まで行くか。習慣化に直結。MVPはアプリ内バッジ。
4. **口座の初期登録負荷**: オンボーディングで口座を何個まで必須にするか（増やすと離脱）。MVPはメイン1口座＋カード引き落とし口座くらい。
5. **複数目標**: 同時に複数目標を持てるようにするか（貯金＋車＋教育）。持てる設計にしつつ、MVPは「主目標1つ」を前面に。
6. **超過/余りの繰越**: 予算の余り・超過を翌月に持ち越すか（`budget-design.md` の未決事項と共通）。持ち越さない方が単純で破綻しにくい。
7. **コーチの口調・頻度**: 毎日話しかけるか、変化があった時だけか。うるさいと開かなくなる。MVPは「異常時＋節目のみ」。

## 8. Claude Code へ渡す一文（実装依頼時）

> Version 2.0 の AI家計コーチを実装してください。ただし「決定的エンジン + LLMナレーション」の原則を厳守し、予算・進捗・達成予測・資金移動提案などの数値は全て純関数（`lib/services/*`）で計算し、LLMには文章化と洞察の選定のみを担わせてください。実装順序は 基盤是正 → 口座モデル → 予算エンジン → オンボーディング/目標 → 目標進捗 → 日次コーチ(ルール版) → LLMナレーション とし、MVPは「目標1つ→自動予算→毎日の進捗と一言」の習慣ループに絞ってください。既存実装（Next.js App Router + Supabase、`lib/cashflow.ts` の純関数スタイル、`docs/budget-design.md`・`docs/v3-architecture-review.md` の設計）を活かし、各エンジンにはユニットテストを付けてください。
